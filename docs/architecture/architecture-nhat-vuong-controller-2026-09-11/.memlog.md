- (direction) User chose Fast path and spine-only deliverable. Draft whole spine with [ASSUMPTION] tags for review; no additional rendering.
- (constraint) Inherited from SPEC.md, not re-decided: .NET MAUI client on Android 8.0+/Windows 10+ (NFR-06); MQTT over TLS with per-device auth (NFR-04); BCrypt passwords (NFR-03); server-side authorisation, client never trusted (NFR-05); state read from control board not inferred (kernel constraint); Vietnamese UI via resource files (NFR-07); service-layer coverage >=60% (NFR-08); command latency <=3s P95 and API <=500ms P95 (NFR-01/02).
- (constraint) Spine binds CAP-1..CAP-23 from SPEC-nhat-vuong-controller at feature altitude; keeps the seven epics coherent.
- (event) Stack verification dispatched to web research before any version is pinned; no technology bound from training data.
- (decision) Paradigm: hexagonal (ports and adapters) on the server. Domain core owns authorisation and policy; driving adapters are REST, scheduler, device-report ingest; driven adapters are MQTT, persistence, notification. Chosen because the same command must be authorised identically no matter which of the three entry points raises it. Maps to NFR-08 service-layer coverage target. [ASSUMPTION]
- (decision) AD-1 single command pipeline. Binds all device-mutating capabilities CAP-4,5,6,9,10,11,20. Prevents three entry points each doing their own authorisation and auditing. Rule: adapters never touch the device port directly, they construct a Command and submit it to the domain CommandService.
- (decision) AD-2 authorisation is a point-in-time lookup against materialised AccessGrant rows, not a rule engine run per command. Timetable import and administrator temporary grants both write the same table. Binds CAP-2, CAP-3, CAP-16. Prevents two divergent rights engines and keeps command authz inside the NFR-02 latency budget.
- (decision) AD-3 offline authority is a server-signed short-lived grant cached on the device, not a client claim. Binds CAP-20 against NFR-05. Prevents the LAN control path becoming an authorisation bypass. Rule: device accepts a LAN command only when accompanied by an unexpired server-signed grant bound to subject, device and window; the app never self-authorises. Grant lifetime no longer than class window plus margin, which also implements CAP-2 automatic expiry.
- (decision) AD-4 the device is the authority on its own state; the server holds a timestamped projection. Binds CAP-7, CAP-8, CAP-21. Prevents the server correcting a device from stale data and the app trusting a cache as truth. Rule: projections carry observedAt and a freshness bound; the server never issues a command purely to reconcile its projection.
- (decision) AD-5 actions taken while offline are reported as facts that already happened, never replayed as commands. Binds CAP-20, CAP-21. Prevents double execution and resurrection of stale intent on reconnect. Rule: device sends an event log on reconnect; server appends to audit and updates projection only.
- (decision) AD-6 device cached schedules are suppressed while the server link is live. Binds CAP-9, CAP-10, CAP-11 against CAP-21. Prevents server scheduler and device firing the same shutdown twice with conflicting audit. Rule: device runs its cached schedule only after link loss exceeds a threshold.
- (decision) AD-7 audit is written by the command pipeline, never by the caller. Binds CAP-18 and every command-raising capability. Prevents rejected commands going unlogged, which US-05 and US-22 explicitly require. Rule: CommandService writes the audit entry before dispatch and updates it with the outcome.
- (decision) AD-8 all instants are UTC end to end; campus local time appears only at the UI edge and at timetable import. Binds CAP-2, CAP-9, CAP-10, CAP-11, CAP-16, CAP-19. Prevents class windows drifting between server, device and app.
- (decision) AD-9 commands are idempotent and correlated by a server-issued command id; devices deduplicate. Binds CAP-6, CAP-8, CAP-20. Prevents retries double-applying and makes per-unit results attributable.
- (decision) AD-10 the device module must not impair manual operation: it sits passive on the control-board bus and a dead or unpowered module leaves the air conditioner operable from its own remote. Binds all device capabilities. Prevents a firmware fault disabling a classroom. [ASSUMPTION] - SPEC.md flagged fail-safe as an open question.
- (decision) AD-11 room-wide actions fan out as individual per-unit commands, never a broadcast. Binds CAP-6. Prevents partial success being unreportable.
- (decision) AD-12 policy thresholds live in server configuration and only the server evaluates them; devices receive resulting absolute times, never the policy. Binds CAP-2, CAP-5, CAP-9, CAP-10, CAP-13. Prevents firmware and client copies of margin, X, N, minimum setpoint and operating hours drifting out of step.
- (question) AD-6 threshold: how long must the server link be down before a device starts acting on its cached schedule? Too short causes double execution during a blip, too long misses a shutdown.
- (question) CAP-10 versus CAP-2 contradiction inherited from SPEC.md is still unresolved and the scheduler design depends on it: does the operating-hours envelope force off a class still in progress?
- (version) .NET 10 LTS (released 2025-11-11, supported to 2028-11-14). .NET 8 and 9 both reach end of support 2026-11-10, two months from now, so neither is a legal starting point. ASP.NET Core 10 ships in lockstep.
- (version) PostgreSQL 18.6 (2026-08-13) with EF Core 10.0.0 and Npgsql. Chosen over SQL Server Express because Express caps the buffer pool at 1,410 MB and compute at 4 cores, which bites at the CAP-22 target of 2,000 users plus 300 devices; the 50 GB size cap would not have.
- (version) Eclipse Mosquitto 2.1.2 (2026-02-09), EPL/EDL. Chosen over EMQX because EMQX moved to BSL 1.1 at 5.9.0; note EMQX is free for accredited academic institutions, so it stays a valid fallback if a management dashboard is wanted for the CAP-22 demo.
- (version) MQTTnet 5.2.0.1603 (2026-07-01). API changed substantially at 5.0: ManagedClient was removed and MQTT 5.0 is now the default protocol on connect, so reconnect and backoff must be hand-written and any pre-2025 sample will not compile.
- (version) ESP-IDF v6.0 (2026-03-24, supported to 2028-09-20) for the device module. [ASSUMPTION] research could not settle whether v6.0 or v6.1 is current stable; confirm at docs.espressif.com/projects/esp-idf/en/stable before the firmware repo is created.
- (version) libsodium 1.0.21 via the Espressif component registry, for Ed25519 grant verification on device.
- (decision) AD-13 device protocol adapters are per-brand and adopted from existing open-source implementations rather than written from scratch; a single ClimateDevice port abstracts them from firmware logic. Binds CAP-4,5,7. Prevents per-brand protocol detail leaking into the command and state paths. Mature prior art exists for every likely brand: Mitsubishi CN105 is a first-class ESPHome component, Daikin S21 has ESP32-Faikin (ESP-IDF native), Panasonic and LG have solid single-maintainer projects, Gree is the least mature and should carry budgeted engineering time.
- (constraint) Licence exposure: ESP32-Faikin is GPL and ESPHome is mixed GPLv3/MIT. Adopting them binds the firmware distribution terms. Acceptable for coursework; must be revisited before any commercial distribution.
- (decision) AD-14 offline grants are signed Ed25519 and verified on device with libsodium; the device holds only a public key. Binds AD-3, CAP-20. Prevents a shared secret replicated across 300 devices becoming a forgery vector if one module is opened. mbedTLS has no Ed25519 support, and mbedTLS ECDSA P-256 verification measures roughly 545 ms to 2 s on a classic ESP32, which is too slow for a control path; HMAC-SHA256 remains the fallback only if per-device secret storage under flash encryption is judged sound.
- (question) Ed25519 verification cost on a classic ESP32 is unmeasured; research estimates 10-30 ms but found no benchmark it trusted. Benchmark before committing AD-14 to a per-command verification design rather than per-session.
- (decision) .NET MAUI 10 pinned for the client as inherited from the user decision, but recorded as a reversible risk: MAUI 10 reaches end of support 2027-05-11 (six months after MAUI 11 ships), a far shorter leash than the .NET 10 LTS date of 2028-11-14, and 2026 reporting describes limited take-up and regression pain. Android 8.0 and Windows 10 targets are safe on both MAUI 10 and 11. Avalonia is the lower-risk alternative covering the same two targets. [ASSUMPTION]
- (decision) Scheduler is a BackgroundService with PeriodicTimer rather than Quartz.NET or Hangfire. Quartz 4.0 is alpha only; Quartz 3.20 and Hangfire 1.8.25 are stable but add a dependency a single-instance campus scheduler does not need.
- (event) Reviewer gate: lint_spine.py PASS with 0 findings. Rubric walker verdict FAIL with 5 critical/high plus 22 lower findings; review at reviews/review-rubric-walker.md.
- (question) CRITICAL from rubric walker: deployment puts API, broker and DB on one campus host, which already satisfies the internet-down scenario CAP-20 describes. The SRS premise for CAP-20/NFR-11 assumes a CLOUD server. Either the server is cloud-hosted (and the LAN path is needed) or campus-hosted (and the LAN path may be unnecessary attack surface). This is a user decision, not an autofix.
- (question) CRITICAL from rubric walker: no trusted device clock decided anywhere, yet AD-3 grant expiry, AD-5 event timestamps, AD-6 link-loss threshold and CAP-21 cached schedules all require an ESP32 to know wall-clock time for hours while disconnected. Implies an RTC in the module BOM - a hardware call.
- (note) CRITICAL from rubric walker: identity and session dimension entirely silent. CAP-1 has no governing AD; nothing fixes the token scheme, the canonical subject identifier that AD-2 lookups and AD-7 audit rows both key on, or BCrypt storage placement. Needs a new AD.
- (note) HIGH from rubric walker: AD-14 wording overstates - device holding only a public key collides with NFR-04 per-device MQTT authentication, which requires the device to hold its own credential. Intent was that the GRANT-SIGNING key is never shared; reword. Device provisioning and trust-store seeding are unmapped, CAP-15 governed only by naming conventions.
- (note) HIGH from rubric walker: operational envelope blank below one campus host - no backup/RPO/RTO, no audit immutability or retention for the Postgres holding CAP-18 evidence, no health-check contract that the deferred CAP-23 supervisor would consume, and no scheduler restart/catch-up semantics given the deliberate no-durable-job-store choice.
- (note) AD-3 additional gap: grant is a pure bearer token with no proof-of-possession or per-command signature, and the Structural Seed draws the LAN hop without TLS, contradicting NFR-04.
